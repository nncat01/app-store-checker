# Реестр приложений App Store

Автоматически обновляемый список приложений из App Store: название,
комментарий, App ID, Bundle ID, разработчик, версия, размер, поддержка
iOS/iPadOS и доступность по 29 регионам. Обновляется 3 раза в сутки через
GitHub Actions.

## Структура

- **`links.txt`** — источник данных. Поддерживает:
  - обычные ссылки на приложение или голый App ID;
  - ссылки на страницу разработчика — подтянутся ВСЕ его приложения одним
    запросом;
  - комментарии, которые попадают в столбец «Комментарий» (см. ниже);
  - свободные пометки через `#` в начале строки — просто игнорируются, ни
    на что не влияют, это чисто для тебя, чтобы не запутаться в списке.
- **`update_apps.py`** — скрипт, который читает `links.txt`, запрашивает
  данные через открытый iTunes Lookup API и пишет/обновляет `apps.csv`.
- **`apps.csv`** — сам реестр. Появится после первого запуска. Смотреть
  можно прямо на GitHub, без скачивания — вкладка с файлом рендерит CSV
  как таблицу.
- **`.github/workflows/update-apps.yml`** — расписание автозапуска.

## Комментарии в links.txt

Для одного приложения (или ссылки на разработчика) — через пробел после
самой ссылки:

```
https://apps.apple.com/us/app/yandex-with-alice-ai/id1050704155 commit: Основной поиск
```

Для группы — строка `commit: текст` сама по себе, дальше все ссылки ниже
получают этот комментарий, пока не встретится пустая строка:

```
commit: приложения Яндекса
https://apps.apple.com/us/app/yandex-with-alice-ai/id1050704155
https://apps.apple.com/us/app/yandex-browser-with-alice-ai/id483693909

https://apps.apple.com/us/app/telegram-messenger/id686449807
```

(Telegram в этом примере комментарий не получит — он уже после пустой
строки.)

Если у приложения есть и групповой, и личный комментарий — в ячейку
попадают оба через пробел, сначала групповой, потом личный.

Если приложение указано и напрямую, и через ссылку на его разработчика —
дублей в таблице не будет, и используется комментарий именно прямой
ссылки на приложение (комментарий аккаунта разработчика для этого
конкретного приложения не учитывается).

## Как включить автообновление

1. Запушь этот репозиторий на GitHub (публичный — тогда Actions бесплатны
   без ограничений; для приватного есть бесплатный лимит минут в месяц).
2. Впиши свои приложения в `links.txt`.
3. Первый запуск можно сделать вручную: вкладка **Actions** → workflow
   **Update app registry** → **Run workflow**. Дальше пойдёт по расписанию
   (06:00 / 14:00 / 22:00 UTC).
4. Проверь, что во вкладке **Settings → Actions → General → Workflow
   permissions** включено **Read and write permissions** — иначе workflow
   не сможет закоммитить обновлённый `apps.csv` обратно в репозиторий.

## Как это работает с датами пропажи

Когда скрипт застаёт момент, что приложение только что стало недоступно в
регионе (было "✓", стало "✗"), рядом фиксируется сегодняшняя дата —
`✗ (24.08.2026)`. Она ставится один раз и не переписывается, пока регион
снова не станет доступен (тогда отметка сбрасывается обратно на "✓").

Если же скрипт **с самого начала** видит регион как недоступный (то есть
приложение пропало оттуда ещё до того, как ссылка попала в `links.txt`) —
дата не ставится вообще, просто "✗" без скобок: настоящую историческую
дату скрипт знать не может, а писать сегодняшнюю было бы враньём.

Если тебе всё-таки известна реальная дата удаления — впиши её вручную
прямо в CSV в точном формате `✗ (ДД.ММ.ГГГГ)`. Скрипт читает содержимое
ячейки перед каждым обновлением и сохранит твою дату как есть, пока
регион не станет снова доступен.

## Ручное редактирование таблицы

`apps.csv` можно редактировать руками:

- **Строки приложений, которых нет в `links.txt`, скрипт не трогает
  вообще.** Так можно завести запись о приложении, которого больше нет ни
  в одном регионе App Store — просто впиши строку по образцу остальных.
- **Для приложений, которые скрипт сам отслеживает**, можно вручную
  проставить дату в столбце региона (см. выше) — она сохранится.
- Поля, которые скрипт обновляет из живых данных API (название, версия,
  размер и т.д.) для ещё существующих в сторе приложений, будут
  перезаписаны свежими данными при следующем запуске — это касается
  только строк, чей App ID снова встретится в `links.txt`.

## Локальный запуск

```bash
pip install -r requirements.txt
python update_apps.py                 # links.txt -> apps.csv
python update_apps.py --no-regions    # без проверки регионов (быстрее)
```

## Заметка про время выполнения

Полная проверка одного приложения по всем 29 регионам занимает ~1.7 минуты
(из-за паузы между запросами — так iTunes API не банит по IP). Ссылка на
разработчика с N приложениями — это N таких проверок за один прогон, так
что для крупных разработчиков (десятки приложений) весь процесс может
занять час и больше. Учитывай это при использовании ссылок на аккаунты.

## Известное ограничение ссылок на разработчика

Если приложение известно скрипту ТОЛЬКО через ссылку на разработчика (не
было и не будет указано напрямую) и в какой-то момент полностью пропадает
из каталога этого разработчика (а не просто из одного региона) — скрипт
перестанет его там видеть и не сможет пометить как "снято отовсюду": оно
просто останется в таблице с последними известными данными, без
обновлений. Для приложений, за полным исчезновением которых важно
следить, надёжнее держать отдельную прямую ссылку — тогда сработает
логика "приложение снято отовсюду" из раздела про даты пропажи.
